# 闲聊分析卡（1.7.0）

解读模板：`app/src/main/java/dev/jev/wechatmood/analysis/ChatTemplates.kt`。
第一轮新增观察：同目录 `ChatFacts.kt`；独立动作库与条件：`ChatActions.kt`。

## 场景库

| 场景 | 4 个分析角度 |
| --- | --- |
| 日常分享 daily | 分享经历、分享成就、吐槽或求办法、延续话题 |
| 邀约安排 invite | 试探邀约、具体安排、婉拒或时间不合适、确认安排 |
| 关心靠近 care | 关心近况、寻求陪伴、相互了解、确认被重视 |
| 玩笑试探 tease | 友好玩笑、试探态度、接受夸奖、停止不舒服的玩笑 |
| 约定记忆 promise | 重视还是记忆、核对具体内容、约定进展、下一步行动 |
| 委屈不满 friction | 倾听感受、尊重暂停、识别明确边界、避免过度解读短句 |
| 解释修复 repair | 对齐问题、具体道歉、补救行动、接受后收尾 |
| 缓和收尾 closing | 气氛缓和、晚安告别、确认完成、自然停顿 |

另外有 8 套不受主场景限制的通用意图卡：拒绝、道歉、感谢、澄清、忙碌、提问、请求、暂停；3 套状态卡：焦虑、困惑、疲惫。合计 43 套。状态卡展示中性「当前状态」，不从疲惫推断关系靠近。

## 一条卡片如何产生

1. 第一轮判断 `scene`、`emotion`、`progress` 和独立交流意图 `speech_act`，以及 `target`、`advice_need`、`commitment`、`own_fault`、`new_topic`、`topic_relation`、`emotion_shift`。扩展焦虑、困惑、疲惫；平静不代表同意，感谢不覆盖后面的明确拒绝。
2. 代码按场景、阶段及明确的观察结果过滤问题与动作。第三方/自身遭遇吐槽和新话题可以纠正旧场景分流；即使场景为 other，明确的交流行为也可进入动作选择。涉及道歉、兑现、告别的动作必须满足对应条件；条件不明确时不提供。
3. 第二轮保留相同的原文、时间和第一轮的**可能出错的路由观察**，但不传递第一轮情绪分布，避免把旧判断当证据。`emotion_review` 和 `speech_act_review` 重新判断；`focus`、`reading_*`、`action` 独立选择；每个 `support_*` 独立核验该动作前提。最终情绪使用复核结果，解读和动作必须兼容复核意图，动作还必须得到明确前提支持。不能在同轮引用其他答案。
4. 每个问题有 `signal`（该模板提出的解释）、`ordinary`（另一种普通解释）、`unclear`（信息不足/不适用）。不能把 signal 当成默认正确答案。
5. 首行为 `Jev + 应用版本`，保留情绪概率及明确意图，可靠解读显示备选概率，可靠动作显示一句建议。底部注明消息发送时间、页面前文实际条数和时间范围、内容缺口。两者独立，不按 signal/ordinary 自动附加建议。
6. 第一轮既无适用问题也无适用动作才只调用一次。第二轮解读和动作都无可靠选择时仅显示情绪；缺失任何实际请求的答案、非法选项或分布均视为可重试失败，不缓存半成品。

当前展示门槛是选项概率至少 0.55 且 confidence 至少 0.35，属于初始产品参数，尚未通过闲聊样本校准。卡片概率是模型对备选解释的估计，不是恋爱概率或事实发生频率。

## 添加和调整模板

每个 `ChatTemplate` 包含唯一 id、scene、标题、问题、两个竞争解释，以及 `onlyDuring`（适用阶段）和 `stopDuring`（停止阶段）。默认在 accepted / closing 时停止；新话题和外部吐槽优先按分享处理。`allowed` 约束涉及双方冲突、约定和告别的问题。

动作放在 `ChatActions.candidates`，每个动作必须有使用条件、给模型的适用描述和给用户的一句文案。先用具体误判样例调整条件，不只增加同义话术。动作不包含操控、欺骗、制造嫉妒或逼迫对方回应的套路，始终保留 none 出口。

两轮最多保留 24 条文字、12000 字符，页面采集最多回看 80 个位置。原始消息保留 ID 和时间，以时间块和同发送者短时段分组而非拼成虚构消息；不会读取后续气泡。时间未知明确标注，时间差由代码计算，不能假定已理解图片或语音。场景接近时保留第二场景少量候选，连同通用卡最多 8 张；明确暂停、拒绝、忙碌、告别优先限制解释范围。

语义对照样例、真实调用方式及结果边界见 [JEV 质量评估](JEV_QUALITY.md)。

离线测试使用人工构造的 Jev 响应，验证路由、两轮传递、停止条件、文案分支和协议校验。它们不能验证真实模型是否理解了聊天；用户实聊验收时重点关注是否贴合、是否重复、是否误判、展示长度和响应等待时间。
