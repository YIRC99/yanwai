# 聊天加号入口调查与安全回退（2026-09-28）

## 当前结论

2.1.10 移除加号面板里的「帮我回」横条及其注入、恢复链路。原生网格新增格子尚未实现；现有证据不足以保证数量、分页与点击映射正确，因此不向原生面板注入任何视图，也不叠加替代按钮。长按标题「分析」→「帮我回 / 上次建议」和消息长按入口仍调用原来的回复界面，回复生成流程不变。

## 已核实的代码与布局证据

- 本机记录 `verification/wechat-view.txt:1281`、`verification/inline-off-view.txt:1281`、`verification/inline-on-view.txt:1250` 都只有隐藏的 AppPanel → 两层 LinearLayout → MMFlipper / MMDotView。面板和内部节点边界为 `0,0-0,0`，未记录展开后的格子或 AppGrid 子节点。记录仅供本地调查，不提交私人页面数据。
- 旧 `ReplyPlusEntry.update` 将原 LinearLayout 从 AppPanel 中取出，添加到新的纵向容器；上方横条占 48dp、分隔线约 1dp，原内容改成 `height=0, weight=1`，新容器填满面板。因而原内容的父节点、布局参数、可用高度和坐标原点均改变。保留点击监听器不等于保留原生测量与触摸行为。
- 旧横条本身可点击且可聚焦；未设置触摸拦截器或 TouchDelegate。代码能证明新增点击区域和原生区域位移，但现有记录没有触摸分发、裁剪或展开后的坐标，不能证明究竟由谁吞掉了某次点击。
- `MessageSniffer.tick` 约每 700ms 扫描，经 `HostUi.showStatus` → `ReplyHostUi.update` 调用注入。不是在经过验证的原生数据初始化点添加项目，可能在展开完成后再次触发布局；延迟本身尚未证实是点击失效根因。
- 面板不可见或未找到时旧逻辑直接返回，保留包裹结构。再次展开只用面板对象和外层容器父节点去重，没有核对原内容是否被宿主替换或重建。`clear` 也仅在外层仍属于原面板或面板为空时尝试恢复，不能证明覆盖全部复用场景。

上述确认了布局干预和生命周期缺口；没有真机触摸轨迹，偶发失效的完整因果链仍未确认。本次消除的是模块对加号面板的这条干预路径。

## 为什么暂不插入原生格子

仓库内未找到当前微信的 AppPanel/AppGrid 实现或宿主 APK；现有布局不包含网格适配器、功能数据、页容量、项目绑定方法或点击回调。仅识别 AppPanel/MMFlipper 不能决定如何安全地插入项目。

真正接入前仍需确认当前安装版本的：

1. 展开首屏与后续页的视图树、格子尺寸、网格/适配器类型及实例关系。
2. 原生功能模型和稳定功能标识（用于识别「相册」），数量、排序、页容量、末页及页指示器的计算链路。
3. 格子绑定、复用及点击分发实现，明确局部位置、全局位置与功能标识的映射；不能简单把索引加一后继续交给旧回调。
4. 切聊天、键盘/表情和数据刷新时的重建入口，以及失败时恢复原始数据和监听器的办法。

布局截图或视图树只能解决第 1 项；仍需对同版本宿主代码或运行时方法关系取得证据，再实现原生数据接入与映射测试。

## 离线与手机验证边界

`ReplyPlusSafetyTest` 保护当前安全回退：聊天刷新/清理不再接入旧注入器，生产代码不保留针对该面板的待用注入实现，标题和消息菜单仍连接现有回复入口。这是源码接线回归，不模拟微信的测量、分页或触摸。未来确认原生契约后，应以对应的数据与点击映射测试替换禁止注入的守卫。

手机最小验收：

1. 覆盖安装本次 Debug APK，彻底结束微信进程后重新打开（仅退回桌面不能卸载旧 Xposed 代码）。本版加号内预期没有「帮我回」横条或新增格子。
2. 同一聊天反复展开/收起三次；左右翻页，分别点相册、拍摄及后续页功能，确认打开的是所点功能，再返回。
3. 切键盘、表情，再切另一位联系人，重复第 2 步；长按「分析」选择「帮我回 / 上次建议」，确认仍能打开原回复界面。

若仍失效，只需反馈微信版本、失效按钮和触发顺序，并从长按「分析」→「导出运行日志」提供日志。若继续原生格子接入，先将手机停在加号首屏并反馈微信版本，之后采集首屏/翻页后的布局与同版本实现；不要求用户猜测混淆类名。当前一般运行日志本身不包含完整网格实现，不能替代以上证据。
